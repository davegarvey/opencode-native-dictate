# OpenCode integration boundary

## Current implementation and acceptance status

The installed OpenCode target is version 2.1.4. Development dependencies match the host: `@opencode/plugin` 2.1.4 and `@opentui/core` / `@opentui/solid` 0.6.8. The v2.1.4 plugin package requires OpenTUI 0.6.8 or newer. `@opentui/core` declares Node >=26.4 and Bun >=1.3.14; OpenCode runs the plugin in its bundled Bun runtime. The plugin loaded in the actual v2.1.4 TUI after the dependency update. These checks do not establish release acceptance; the full editor-context and audio matrix remains outstanding.

The isolated TUI configuration used a temporary `cli.json`, with this repository registered as a path plugin. It loaded the root `tui.tsx` entrypoint. A separate minimal lifecycle probe recorded setup and its cleanup callback after exiting the isolated TUI. The user's global OpenCode configuration was not changed. Reload cleanup for the full plugin has not been verified. The global registration helper now supports OpenCode's object form with plugin-specific options; its JSONC edits are covered using temporary configurations.

## Evidence collected

- Against the real OpenCode editor on 2.1.4, the synthetic transcript inserted into an empty prompt and in the middle of a populated draft; Unicode insertion was visually correct. Selection was refused with an actionable message. The editor's `undo()` action directly reversed the synthetic insertion and restored the prior draft, confirming that the insertion is in the editor undo history. `Cmd+Z` did not undo in the user's Ghostty session; an attempted key sequence produced a literal `v`. Keyboard-driven undo remains unverified, and the plugin adds no custom undo menu command. Beginning/end insertion, file-reference preservation, pasted-block preservation and the full undo matrix also remain unverified.
- The start command was refused in the command palette (`modal` mode) and in shell mode. OpenCode v2.1.4 source inspection confirms autocomplete uses `autocomplete` mode, forms and dialogs use non-base modes, and the prompt loses focus when disabled. Host unit tests cover these mode/route guards, no focused editor, single-line inputs and busy sessions. Disabled-form and non-prompt textarea refusal have not been exercised separately in the live TUI.
- A delayed fake backend verified Enter consumption during recording and transition to transcribing, Escape cancellation during startup, repeated Enter suppression after completion, and the ordinary fresh-Enter pass-through in unit tests. The same safety probe was exercised in the isolated 2.1.4 TUI. The real TUI remained on the prompt after a repeat event; an empty prompt was used when checking the normal Enter path so the check could not send a model request.
- TUI setup disposal now clears its timers and input guard, resets session state, and makes retained command callbacks inert. The built TUI entry is exercised through three setup/dispose cycles in `test/tui-lifecycle.test.mjs`; listener counts return to baseline each time. OpenCode 2.1.4's `keymap.layer` contract removes command registrations on plugin deactivation, but repeated registration counts have not yet been checked in a live reload.
- The current automated suite passes: Swift permission/audio-format tests, 9 Python worker and model-download recovery tests, and 49 Node host/controller/backend/config tests. `npm run check` passes. The user confirmed one real Parakeet dictation produced the expected text after the explicit model-type fix; latency and reference-corpus accuracy remain unmeasured. The default leader chord is now `<leader>d`, but live Ghostty delivery remains to be confirmed. The synthetic and fake safety probes are hidden from the command palette and slash completion. The earlier audit findings were addressed with the pinned `seroval` and `seroval-plugins` overrides described below; the current lockfile audit reports zero findings. These checks do not substitute for the unfinished editor-context and audio acceptance matrix.

## Host API assumptions

The public OpenCode plugin context does not expose a prompt object or a prompt-disabled flag. The adapter identifies a prompt conservatively by requiring a `home` or `session` route, base keymap mode, normal prompt-footer mode, an idle session when applicable, and a focused `TextareaRenderable` that is not an `InputRenderable`. It refuses selected text. The adapter inserts through the focused editor's `insertText` method and uses `cursorCharacterOffset` when available.

The plugin context does not expose OpenCode's internal `keymap.intercept` method at runtime. Enter and Escape are currently guarded through `renderer.keyInput.prependListener`, which assumes the renderer key handler is an EventEmitter and that prepended listeners run before OpenCode's keymap and editor submit handlers. The fake-session TUI probe showed that ordering on 2.1.4. The repeat guard also relies on the host key event's `repeated` flag and `keyrelease` event when the terminal provides them. These low-level, version-sensitive assumptions have been exercised against 2.1.4 but still need the remaining host/editor acceptance checks before claiming compatibility.

## Dependency audit

The OpenCode 2.1.4-compatible `@opentui/solid` 0.6.8 package requires `solid-js` 1.9.12 exactly. That Solid release resolves `seroval` and `seroval-plugins` to vulnerable 1.5.x versions. The advisories identify 1.6.2 and 1.6.3 as patched releases; `package.json` uses npm overrides to pin both transitive packages to 1.6.3 while preserving the host-matched OpenCode, OpenTUI and Solid versions. A clean lockfile install now reports zero npm audit findings; `npm test` and `npm run check` pass with those overrides. See [GHSA-p6vx-979v-rg4c](https://github.com/advisories/GHSA-p6vx-979v-rg4c) and [GHSA-jp82-f5mq-hwhp](https://github.com/advisories/GHSA-jp82-f5mq-hwhp). Recheck these packages when OpenCode/OpenTUI publishes a compatible update, and remove the overrides only after confirming the new dependency tree is patched and compatible.

The user has installed the isolated runtime and pinned Parakeet assets; their `npm run doctor` reports the MacBook Pro microphone as the default input. Their first stop-to-transcribe attempt exposed that MLX Audio inferred architecture from the local revision-hash directory. The worker now passes the selected architecture explicitly and a regression test covers both backend mappings. The user confirmed a successful real dictation with correct text after that fix. This execution environment cannot access a Metal device or audio input, so it cannot independently repeat the user's hardware check. The new default `<leader>d` chord still needs a live Ghostty check. USB disconnect, reload and benchmark checks remain open. Global operation was checked from two temporary project directories.
